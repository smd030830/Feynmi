- 환경: 팀 Firebase 프로젝트, 구글 로그인, 로컬 Docker(DB `feynmi_minseok2`), OpenAI 키 없음

### PDF: 컴퓨터보안 강의 슬라이드 (40쪽, 2.2MB)

결과: 분석 완료, 40쪽 모두 글자 저장, 빈 쪽 0, 약 1분 안에 끝남.

| 구분 | 내용 |
|---|---|
| 잘 됨 | 쪽 순서와 글머리 구조 유지. 그림 속 글자 상당수 읽음 (예: 협박 메일 그림, 두 모델 비교표) |
| 문제 A (높음) | 본문 한글 띄어쓰기가 사라짐 ("적절한권한을가진인가자만이…"). PDF가 띄어쓰기를 글자 간격으로만 저장했기 때문이다. pypdf `extraction_mode="layout"`로 읽으면 복원되는 것을 확인했고, 빠지는 글자는 0이다. 연속 공백 정리와 2단 문서 확인이 필요하다 |
| 문제 B (중간) | 도표·아이콘 그림에서 엉터리 글자가 남음 ("ESE acco pasa…", "£1-@B@B-o"). 신뢰도 40 이상이라 버려지지 않았다 |
| 문제 C (중간) | 그림 속 한글 오독 ("Secret인"→"Secreto!", "정보를"→"SHS"). OpenAI 키를 넣으면 AI가 다시 읽는다 |
| 문제 D (낮음) | 매 쪽 머리글("컴퓨터 보안 / 정보보호 개론…")이 38번 반복된다 |

### PPTX: 게임 개발 수업 교안 (16슬라이드, 3.8MB, Unity 코드 캡처 위주)

결과: 분석 완료, 16쪽.

| 구분 | 내용 |
|---|---|
| 잘 됨 | 슬라이드 제목, 글 상자, 코드 캡처 속 한글 주석은 대체로 읽음 |
| 정상 판단 | 7, 10, 12쪽은 게임 화면 캡처만 있어 OCR이 엉터리(신뢰도 33~36)를 냈고, 규칙대로 버렸다 → 제목만 남음 |
| 문제 E (중간) | 코드 캡처에서 편집기 줄 표시가 `\|`, `!`, `i` 같은 군더더기로 줄 앞에 붙음 |
| 문제 F (중간) | 코드 식별자 오독 ("roomOptions"→"「0000011006.160060", "null"→"0411"). 한영 혼합 판독(`kor+eng`)이 영문 코드를 한글·숫자로 착각한다. AI 재판독 대상이지만 자료당 20번 한도가 있다 |

### PNG: 코드 편집기 화면 캡처 (90KB)

| 구분 | 내용 |

### JPG: 태블릿 손글씨 필기 (화면 설계 스케치, 681KB)

## 7. 2026-11-14 · TXT·DOCX·HWPX·HWP 지원 추가 (제안 I, 실험)

- 이유: 강의 자료와 필기는 PDF·PPTX·이미지 말고도 한글 문서(학교 공지·과제 안내·보고서), 워드, 메모장이 흔하다. 모두 글자로 바꿔 같은 길로 보내면 된다.
- 방식: 확장자마다 읽는 방법만 추가하고, 그 뒤(OCR, 조각, 임베딩)는 기존과 같다. 쪽은 사용자가 넣은 쪽 나누기에서만 나눈다(워드·한글은 쪽이 파일에 저장되지 않음).

| 형식 | 시험 | 결과 |
|---|---|---|
| TXT | UTF-8 / CP949(예전 메모장) / UTF-16·UTF-8 BOM, 바이너리를 .txt로, 빈 파일 | 모두 글자 정상 / 바이너리는 `unsupported_format` / 빈 파일은 `no_extractable_text` |
| DOCX | 제목·문단·표·쪽 나누기·그림이 든 문서 (python-docx로 생성) | 2쪽으로 나뉨, 표는 "상태 \| 설명" 행으로, 그림은 OCR로 해당 쪽에 붙음. 다른 오피스 ZIP은 거절 |
| HWPX | 문단·표·탭·쪽 나누기·그림이 든 문서 (규격대로 생성), 압축 폭탄 | 정상 / 풀린 크기 상한 초과는 `file_too_large` |
| HWP | **실제 과제 결과보고서 HWP** (HWP 5.1, 압축, 그림 7장) | 2쪽, 본문·표 글자 순서대로, 2쪽의 그림 7장(구조도·화면 캡처)을 OCR로 읽음, 약 10초 |
| HWP | 규격대로 만든 레코드: 제어 문자, 긴 레코드, 암호·배포용 표시 | 탭·줄바꿈만 남고 제어 문자 제거 / 암호·배포용은 `corrupted_file` / OLE 아님은 `unsupported_format` |

- 함께 고친 것: 한글 문서의 기호 문자(U+F0099 등 글꼴 전용 영역) 정리를 공통 정리(`normalize_text`)로 옮겨 모든 형식에 적용했다.
- 바뀐 것: DB 형식 제약(마이그레이션 0004), 업로드 허용 확장자, 화면 안내 문구. `.ppt`·`.doc`는 여전히 미지원으로, 새 형식으로 저장해 달라고 안내한다.
- 시험: 19개 추가, 백엔드 275개 통과. 기존 시험 중 docx·txt를 "거절돼야 함"으로 쓰던 3개는 doc·xlsx로 바꿨다.
- 커밋: `f59edca`
- 미정: HEIC(아이폰 원본 사진)는 팀과 방식 논의 중이다. 업로드 때 JPG로 바꿔 저장할지, 원본을 보관하고 분석할 때 바꿀지.

## 안정된 부분

| 영역 | 근거 |
|---|---|
| 로그인 → 백엔드 인정 (팀 Firebase) | 실제 구글 로그인 200, 가짜·없는 출입증 401 |
| 업로드 규칙 (형식·용량·빈 파일·동의·닉네임) | 종단 간 시험 2회와 실제 화면에서 모두 기대대로 |
| 상태 흐름과 화면 자동 갱신 | 대기 → 추출 중 → 완료/실패, 2초 폴링 |
| 실패 판정 (빈·잘림·암호·형식 위장·쪽수 초과) | 모두 맞는 실패 코드 |
| 본인 자료만 접근 | 다른 사용자 404 |
| 재시도, 서버 재시작 복구 | 실패만 재시도, 재시작 시 갇힘 없음 |
| 저장 | DB `materials.page_texts`(쪽별 글자), 원본 파일 보관 폴더 |
| PDF·PPTX 글자 층 추출 | 쪽 순서·구조·띄어쓰기 유지 (6번에서 A 수정 후) |
| 사진 방향 보정, 투명 배경, 작은 그림 확대 | 시험 통과 |
| OCR 엉터리 버리기 | 손글씨·게임 화면은 그림째, 도표 엉터리 줄은 줄 단위로 버리고 정상 글자는 남김 |
